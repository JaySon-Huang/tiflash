# Add TSV Input Mode to `dttool bench`

## Summary

`tiflash dttool bench` should support a file-backed benchmark mode that reads
the TSV data file and schema JSON generated by `tiflash dttool generate`,
reconstructs `Block` objects from those files, writes the blocks into DMFile,
and then runs the existing DMFile read benchmark. In this mode, benchmark input
data comes from files instead of being randomly generated inside
`DTToolBench.cpp`.

## Context

### Current State

`tiflash dttool generate` is implemented in
`dbms/src/Server/DTTool/DTToolGenerate.cpp`.

It currently:

- Requires `--rows`, `--columns`, `--output`, and `--schema`.
- Requires `--rows` to be a multiple of `DEFAULT_MERGE_BLOCK_SIZE` (`8192`).
- Reuses `DTTool::Bench::createColumnDefines` and
  `DTTool::Bench::genBlocks`.
- Writes a TSV file without a header row.
- Encodes nullable values as `\N`.
- Writes schema JSON with this shape:

```json
{
  "columns": [
    {
      "name": "_tidb_rowid",
      "type": "Int64"
    }
  ]
}
```

`tiflash dttool bench` is implemented in
`dbms/src/Server/DTTool/DTToolBench.cpp`.

It currently:

- Parses benchmark options such as `--rows`, `--columns`, `--sparse-ratio`,
  `--str-len`, `--random`, `--repeat`, `--write-repeat`, and DTFile format
  options.
- Calls `genBlocks(random_seed, num_rows, num_cols, str_len, sparse_ratio,
  logger)` whenever `write-repeat > 0`.
- Writes the generated blocks through `DMFileBlockOutputStream`.
- Restores the generated DMFile and measures read performance through
  `DMFileBlockInputStreamBuilder`.

The repository already has a `TabSeparated` / `TSV` input format in
`FormatFactory`. It reads rows with `TabSeparatedRowInputStream`, which uses
`deserializeTextEscaped`. `Nullable` columns already parse `\N` as null.

### Problem Statement

The current benchmark always generates blocks in memory when it needs to write
a DMFile. This makes it hard to benchmark a fixed generated data set, to reuse
the same input across runs, or to separate data generation cost from DMFile
write and read cost.

`dttool generate` now provides a reusable TSV plus schema pair. `dttool bench`
should be able to consume that pair directly and build benchmark blocks from
the persisted data.

### Constraints

- The input format is the output format produced by `dttool generate`.
- The TSV file has no header row.
- Nullable values are represented as `\N`.
- The schema JSON contains only column names and type names.
- The schema JSON does not contain column IDs, row counts, random seeds, or
  generation parameters.
- The generated row count is expected to be a multiple of `8192`.
- Existing random-data benchmark behavior should remain available for backward
  compatibility unless a separate deprecation decision is made.

## Goals

1. Add a `dttool bench` mode that reads blocks from `generate` output files.
2. Avoid calling random block generation in file-backed mode.
3. Build DMFile write input from the TSV data and schema JSON.
4. Preserve the existing DTFile write/read benchmark pipeline after blocks are
   loaded.
5. Validate schema and TSV consistency before starting DMFile writes.
6. Keep current random benchmark behavior available when no input files are
   provided.

## Non-Goals

- Do not turn `dttool bench` into a general-purpose table import tool.
- Do not support arbitrary schema JSON beyond the `dttool generate` schema
  contract.
- Do not add TSV headers or `--with-header`.
- Do not add CSV support.
- Do not change `migrate` or `inspect`.
- Do not benchmark TSV parsing as part of DMFile read performance.

## Design

### Command Interface

Add file input options to `dttool bench`:

| Option | Description |
| --- | --- |
| `--input` | Path to the TSV data file generated by `dttool generate`. |
| `--schema` | Path to the schema JSON file generated by `dttool generate`. |

File-backed mode is enabled only when both `--input` and `--schema` are
provided.

Rules:

- Supplying only one of `--input` or `--schema` is invalid and returns
  `-EINVAL`.
- In file-backed mode, `--rows`, `--columns`, `--sparse-ratio`, `--str-len`,
  and `--random` must not drive block generation.
- The benchmark should log the actual loaded row count, column count, block
  count, and effective uncompressed bytes.
- Existing DTFile options such as `--version`, `--algorithm`, `--frame`,
  `--repeat`, `--write-repeat`, `--encryption`, `--workdir`, and `--clean`
  keep their existing meaning.

### Input Flow

The file-backed flow should be:

```text
schema.json + data.tsv
        |
        v
parse schema JSON -> build ColumnDefines and sample Block
        |
        v
parse TSV with TabSeparated input, max block size = 8192
        |
        v
vector<Block> + vector<BlockProperty>
        |
        v
existing DMFile write benchmark
        |
        v
existing DMFile restore/read benchmark
```

### Schema Handling

The schema loader should read `columns` from the JSON file. Each column entry
must contain:

- `name`
- `type`

Because the schema JSON does not contain column IDs, `bench` should only accept
schemas compatible with `dttool generate`.

Column ID reconstruction:

- `_tidb_rowid` maps to `MutSup::extra_handle_id`.
- `_INTERNAL_VERSION` maps to `MutSup::version_col_id`.
- `_INTERNAL_DELMARK` maps to `MutSup::delmark_col_id`.
- User columns use deterministic IDs based on their position after the hidden
  columns, starting from `3`, matching `createColumnDefines`.

Type reconstruction:

- Use `DataTypeFactory::instance().get(type_name)` to construct the data type.
- Unsupported or unparseable type names are invalid.
- The supported initial type set is the type set emitted by `dttool generate`:
  `Int64`, `UInt64`, `UInt8`, and `Nullable(String)`.

Validation:

- The schema must contain at least the three hidden columns.
- The schema column order must match the TSV column order.
- Hidden columns must have the expected names and types.
- User column IDs must be deterministic and stable across runs.

### TSV Handling

The TSV loader should use the existing `TabSeparated` input format rather than
manual string splitting:

- Create a sample `Block` from the parsed schema.
- Open the TSV file with `ReadBufferFromFile`.
- Call `context.getInputFormat("TabSeparated", buffer, sample,
  DEFAULT_MERGE_BLOCK_SIZE)`.
- Read all blocks into memory before starting the DMFile write benchmark.

Requirements:

- The TSV file must not have a header.
- Every row must have exactly the number of fields declared by the schema.
- `\N` must round-trip as null for nullable string columns.
- The input must contain at least one row.
- The final loaded row count must be a multiple of `8192`.
- Each loaded block should contain `8192` rows. A partial final block is invalid
  for this generated-data benchmark mode.

### Block Properties

For blocks loaded from TSV, create matching
`DMFileBlockOutputStream::BlockProperty` entries:

- `effective_num_rows` is `block.rows()`.
- `gc_hint_version` should be deterministic and monotonically increasing by
  block order.
- Other fields should follow the existing default behavior unless the benchmark
  needs a specific value.

`effective_size` should be computed from the loaded blocks so write throughput
continues to use the actual uncompressed input size.

### Existing Random Mode

When neither `--input` nor `--schema` is provided, `bench` should preserve the
current random generation path:

```text
genBlocks(random_seed, num_rows, num_cols, str_len, sparse_ratio, logger)
```

This keeps existing benchmark commands working while enabling reproducible
file-backed runs.

### Producer Contract Hardening

The reader and writer should share one TSV contract. The preferred contract is
ClickHouse-style `TabSeparated` escaped text:

- Nulls are `\N`.
- Strings are escaped in the way `deserializeTextEscaped` expects.
- Tabs, newlines, and backslashes inside string values must be escaped if they
  can appear in generated values.

If `dttool generate` writes a value format that is not parseable by
`TabSeparated` with identical logical values, update `generate` to emit
`serializeTextEscaped` output for each column type, or document and test the
intentional difference.

`dttool generate` should also fail if the schema file cannot be opened or
written. A missing schema file must not be treated as a successful generation.

## Failure Handling

Return `-EINVAL` and avoid starting DMFile writes when:

- Only one of `--input` or `--schema` is provided.
- The schema file cannot be opened or parsed.
- The schema JSON is missing `columns`, `name`, or `type`.
- The schema is not compatible with `dttool generate`.
- The TSV file cannot be opened.
- TSV parsing fails.
- The loaded row count is zero.
- The loaded row count is not a multiple of `8192`.
- A final partial block is encountered.

Errors during DMFile write or read should continue to use the existing `bench`
exception logging behavior.

## Validation Strategy

Add focused tests under `dbms/src/Server/tests/gtest_dttool.cpp` or a dedicated
DTTool test file.

Functional tests:

- Generate a TSV/schema pair with `DTTool::Generate::generateEntry`, then load
  it through the new bench loader and verify row count, block count, and column
  count.
- Verify `\N` in generated TSV becomes null in `Nullable(String)` columns.
- Verify the loaded block names and types come from schema JSON.
- Verify the loaded hidden columns map to the expected internal column IDs.
- Verify missing `--input` or missing `--schema` returns `-EINVAL`.
- Verify malformed schema JSON returns `-EINVAL`.
- Verify schema/TSV column count mismatch returns `-EINVAL`.
- Verify row counts that are not multiples of `8192` are rejected before DMFile
  write starts.

Benchmark path tests:

- Run `bench` in file-backed mode with a small generated input and
  `--write-repeat 1 --repeat 1`.
- Restore the written DMFile and verify the total row count matches the TSV row
  count.
- Run the same file-backed input twice and verify the benchmark writes
  equivalent DMFile block structure.

Suggested validation command:

```bash
cmake --build --preset unit-tests
cmake-build-debug/dbms/gtests_dbms --gtest_filter=*DTTool*
```

## Risks and Mitigations

1. Schema JSON does not include column IDs.
   Mitigation: support only `dttool generate` compatible schemas and
   reconstruct IDs deterministically.

2. TSV producer and consumer can drift.
   Mitigation: add round-trip tests that generate TSV, read it back into
   blocks, and compare logical values for the supported type set.

3. TSV parsing cost can pollute write benchmark timing.
   Mitigation: load all TSV blocks before starting the timed DMFile write loop.

4. Large TSV files can require large memory because blocks are loaded before
   writes.
   Mitigation: match the existing random path first, which already stores all
   generated blocks. Streaming TSV into each write repeat can be considered
   later if memory becomes a bottleneck.

5. Existing random benchmark commands may rely on current defaults.
   Mitigation: keep random mode unchanged when file input options are absent.
